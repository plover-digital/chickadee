# Warm runner startup and tool setup investigation

Three paired, no-workload probes found a median **8.7 seconds** from workflow
creation to the first command on Chickadee, versus **6.5 seconds** on a standard
public GitHub Ubuntu runner: about **2.2 seconds extra** on Chickadee in this
small sample. The existing Go setup stage also costs approximately nine seconds on both
providers, but workload tool installation is outside the platform optimization
focus. Image owners may choose their own tools and caches.

## Startup experiment

The manual `.github/workflows/startup-probe.yml` runs two independent jobs in
parallel, one per provider. Each executes only `date --utc`, with no checkout,
setup action, artifact upload, build or job dependency. Three workflow runs
were dispatched sequentially after prior jobs finished and a new independent
warm guest reached READY. The controller was instrumented with numeric elapsed
times for guest boot, JIT generation, configuration ACK and listener launch.
No credentials, configuration payloads or arbitrary guest strings are logged.

The deployed profile was 4 vCPU / 4 GiB per guest, warm 1, maximum 2, unchanged
image/runner version. The controller source and workflow were commit
`e09d04d3a513b4eeff2c3b218524afb7cf1ae0b6`. All six first attempts passed:

- [Probe 1](https://github.com/plover-digital/chickadee/actions/runs/37474629802)
- [Probe 2](https://github.com/plover-digital/chickadee/actions/runs/37474665814)
- [Probe 3](https://github.com/plover-digital/chickadee/actions/runs/37474707665)

[Sanitized raw samples](2026-10-06-startup-samples.json) include public run IDs,
GitHub timestamps, first-command timestamps and controller elapsed times.
They omit host names, addresses, App metadata and VM identifiers.

| Measurement | Chickadee median (range) | GitHub median (range) |
| --- | ---: | ---: |
| Workflow created → job started, seconds | 7 (7–8) | 5 (5–5) |
| Workflow created → first step, seconds | 8 (8–9) | 6 (6–6) |
| Workflow created → actual first command, seconds | 8.722 (8.091–9.331) | 6.512 (6.316–6.780) |
| Job execution, seconds | 3 (3–3) | 3 (3–4) |

GitHub workflow/job/step metadata has one-second timestamp resolution. The
command prints guest wall-clock time with fractional seconds; host clock
synchronization was verified, but cross-system clock offsets were not
independently calibrated. Fractional digits are retained for provenance,
not a claim of millisecond end-to-end accuracy. These probes measure manual
workflow dispatch, not commit-push latency, general queue latency, cold boots,
capacity exhaustion or burst behavior.

## Chickadee phase breakdown

| Phase | Median | Range |
| --- | ---: | ---: |
| Workflow creation → controller sees assigned demand | 4.143s | 2.957–4.576s |
| Demand observed → VM reservation | 0.067s | 0.067–0.070s |
| JIT generation request | 459ms | 324–723ms |
| Serial send → guest ACK | 128ms | 126–147ms |
| Serial send → local listener launch | 132ms | 130–150ms |
| Reservation → GitHub job started | 3.357s | 2.787–3.976s |

ACK and listener-launch times have the same starting point and must not be
added together. Medians from different samples also need not sum to the median
total. The demand timing includes GitHub scheduling and scale-set delivery;
it does not isolate long-poll transport latency. `GetMessage` already long-polls;
there is no fixed polling sleep to shorten. Demand-to-reservation includes
local actor work and durable credential intent.

RUNNING means the guest successfully spawned Runner.Listener. It does **not**
mean GitHub connection, registration readiness or job assignment. The interval
from reservation to GitHub job start includes JIT, serial delivery, listener
startup, connection and GitHub matching. Only the first three phases have
independent local timings; the remaining interval cannot yet be attributed
between network and GitHub processing.

The independently booted initial warm guest took 6.130 seconds to reach READY.
That boot was completed before dispatch and therefore was outside the probes'
startup critical path. Replacement guests were prebooted independently;
no snapshots or suspension were used. Each spent VM and overlay was destroyed
and the pool replenished. The smaller serial/JIT intervals do not justify
adding snapshot machinery or weakening the no-reuse rule.

## Go setup investigation

In the first expanded benchmark sample, Chickadee `setup-go` logs showed:

- version lookup/download: approximately 1.8 seconds;
- extraction: approximately 1.6 seconds;
- adding the extracted distribution to the tool cache: approximately 4.6 seconds;
- complete action: approximately 8 seconds.

The matching hosted sample also downloaded the pinned version, extracted it
and copied it into its tool cache; that copy took approximately 5.9 seconds.
Across all expanded benchmark samples, the complete action median was 9 seconds
on both platforms. These logs explain why a prepopulated hosted tool cache did
not give this particular version an advantage. `cache: false` disables module/
build cache restoration; it does not eliminate the action's tool installation
and tool-cache copy.

Official [setup-go documentation](https://github.com/actions/setup-go/blob/v7.0.0/README.md)
says it checks the local tool cache first. The
[runner implementation](https://github.com/actions/runner/blob/v2.337.0/src/Runner.Worker/JobRunner.cs)
sets the tool-cache directory in the job context. Tool preinstallation belongs to an image owner's workload choices, not to the
controller's defaults. Chickadee does not assume Go, a specific user toolchain
or a future shared cache. The measured cache-copy cost is retained as an
explanation of this benchmark, not a plan to bake Go into every guest.

The current image has **not** been modified by this investigation. Any future
image change must remain credential-free, reproducible and compatible with
fresh overlays. Do not introduce a shared writable host cache or reuse spent
VMs. Benchmark the action before and after; the full nine seconds cannot be
assumed removable without that measurement.

## Next measurements

Prioritize generic provisioning and runner connectivity. A subsequent
[controller ordering experiment](2026-10-06-startup-overlap.md) removes an
avoidable API wait before forwarding assigned demand. Collect more paired
startup samples and, if useful, a controlled cold-pool probe. A connected-to-GitHub
milestone would help explain the residual startup interval, but it requires a
safe, reliable signal rather than treating local RUNNING as connection proof.
Concurrency-two throughput and commit-push-to-first-command latency remain
unmeasured. Three successful probes do not establish service-level guarantees.

To reproduce: dispatch `startup-probe.yml` on main after confirming a warm guest
and no other jobs, wait for both jobs to finish, confirm destruction/replenishment,
and repeat. A new deployment must adapt the repository guard and permit the
exact workflow ref in its dedicated runner group. Correlate the public run/job
metadata with the private controller journal by runner name/VM ID; publish only
sanitized durations, not management credentials or private infrastructure data.
