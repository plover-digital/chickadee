# Chickadee versus GitHub-hosted Ubuntu: initial benchmark

A [follow-up with 4 vCPU / 4 GiB guests](2026-10-06-expanded.md) reduced
Chickadee build/test time by 23%; the measurements below describe the original profile.

On 2026-10-06, the deployed Chickadee profile took a median **45.8 seconds**
for cold builds plus race tests, compared with **39.1 seconds** on the standard
public GitHub-hosted Ubuntu runner: **17% longer**. Complete successful job
execution took **64 versus 56 seconds**, or **14% longer**.

These are measurements of two different configured services, not an estimate
of QEMU overhead. Three samples per platform are too few for a general capacity
or reliability claim.

## Method and provenance

[Benchmark workflow and logs](https://github.com/plover-digital/chickadee/actions/runs/37466317267)
ran the same source commit `f8b074b29913590cebe677e5ad208ecc6cfa5abd` and
Go 1.26.3 on fresh Ubuntu 24.04 guests. Its matrix ran sequentially, without
competing jobs during measurement. The workflow disables setup-go caching;
`scripts/benchmark.py` assigns empty, isolated Go build and module caches for
each sample. Commands run in this order: module download, `make build`,
`make test`, then the same build and test again. `make test` includes Go race
tests and the Python App-helper tests. The cold test follows the cold build,
so these are the project's normal sequential build/test commands, rather than
two independently cleared caches.

Chickadee: 2 vCPU, 2048 MiB configured memory, 16 GiB qcow2 root overlay backed
by local NVMe, warm pool 1, maximum 2 guests. Its guest kernel was
6.8.0-142-generic. GitHub: 4 visible CPUs, approximately 16 GiB memory,
kernel 6.17.0-1022-azure. GitHub's
[official public runner specification](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)
labels the standard Ubuntu profile as 4 CPUs, 16 GB RAM and 14 GB SSD.
Both platforms reported the same Go version. CPU count and guest memory were
recorded inside each job; we did not measure CPU frequency, storage throughput
or host contention.

Raw successful samples, including individual timings and measured hardware:
[2026-10-06-samples.json](2026-10-06-samples.json).

## Results

Times below are medians in seconds; ranges show all three successful samples.

| Measurement | Chickadee median (range) | GitHub median (range) |
| --- | ---: | ---: |
| Cold build | 15.240 (15.153–15.334) | 11.694 (7.257–12.052) |
| Cold race/Python tests | 30.650 (30.515–30.692) | 27.358 (20.197–27.413) |
| Cold build + tests | 45.845 (45.755–45.984) | 39.107 (27.454–39.410) |
| Module download | 0.351 (0.346–2.581) | 0.255 (0.075–0.270) |
| Go setup | 9 (8–10) | 9 (8–11) |
| Checkout | 1 (1–2) | 1 (1–2) |
| Complete successful job | 64 (63–65) | 56 (42–57) |
| Cached build | 0.145 (0.144–0.148) | 0.107 (0.071–0.116) |
| Cached tests | 0.248 (0.246–0.253) | 0.193 (0.126–0.194) |

Command timings use Python's monotonic clock. Checkout, setup and job times
come from GitHub API timestamps with one-second resolution. Complete job time
includes setup, the cached repeat, artifact upload and post steps; it excludes
queue waiting. Matrix waiting is intentional and is unsuitable for measuring
runner startup latency. This run does not establish a startup latency comparison. A subsequent
[paired warm-startup investigation](2026-10-06-startup.md) measures that separately.
Cached Go tests reuse successful test results; their timing does not measure
fresh test execution. No cache persists between Chickadee guests.

## Failure discovered and fixed

The original third Chickadee attempt failed before timed compilation. GitHub
reported lost runner communication and declared failure after ten minutes.
Host evidence identified a QEMU thread-creation abort: the service cgroup
reached its 100-task ceiling and recorded a task-limit rejection. This was a
reliability failure, not a ten-minute compilation or proven network-download delay.

The installer had budgeted too few host threads for QEMU's disk-I/O pools.
Commit `2867deb` increases the finite service budget to
`64 + max_vms * (cpus + 160)`; the pilot allowance is now 388 tasks.
CPU, memory, disk and VM concurrency limits are unchanged. CI passed, then
only the failed benchmark was rerun using its original source SHA. It succeeded
and its VM/overlay were destroyed, with a credential-free warm replacement
ready. The cgroup rejection count remained at one after correction.

The table uses the repaired successful third attempt. The initial failure
remains visible in workflow attempt 1 and must not be interpreted as a successful
sample. One rerun validates this observed correction, not broad reliability.

## Interpretation and next measurements

Chickadee has half the visible CPUs and one eighth the configured memory.
Those resources are plausible contributors to the difference, but this experiment
cannot apportion the gap among CPU model, CPU count, disk, memory and KVM/QEMU.
There is no evidence here that memory pressure caused the normal timing gap.
The public runner's third sample was substantially faster than its first two,
showing that this small comparison also includes provider variability.

For this Go workload, healthy Go setup medians were equal. Preinstalling the
pinned Go toolchain could eliminate setup work for a dedicated image, but tool
setup did not explain the successful-job performance difference in this run.
Before increasing deployed resources, compare both platforms with fixed Go
parallelism and collect more samples; then repeat with a 4-vCPU Chickadee profile
if that resource cost fits the intended deployment. Larger builds, memory-heavy
tests, network and storage workloads need their own measurements. We have not
measured burst capacity, cost per job or paid-service readiness.

## Repeat

On this deployment, dispatch `.github/workflows/benchmark.yml` on `main` after
other jobs finish. A new installation must first provision its image, App,
network and pool and allow this exact workflow in its dedicated runner group.
The checked-in workflow guards the pilot repository; change that guard to your
own repository and review runner-group policy when adapting it. Download the
six JSON artifacts and inspect failures as well as successful timings. The
workflow's artifact retention is seven days; these committed samples preserve
the results independently.
