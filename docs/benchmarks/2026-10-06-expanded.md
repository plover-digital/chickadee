# Resource increase: 4-vCPU / 4-GiB Chickadee

Increasing each pilot guest from 2 vCPU / 2 GiB to **4 vCPU / 4 GiB** reduced
median cold build plus race/Python test time from **45.845 to 35.251 seconds**:
**23.1% less time**. A fresh standard public GitHub Ubuntu baseline took
**39.907 seconds**, so the expanded Chickadee profile took **11.7% less time**
in this run. All six jobs succeeded on their first attempt.

[Workflow run](https://github.com/plover-digital/chickadee/actions/runs/37470443798)
used commit `eb3f269eee147f9683780805b8cc3ff7be028484`, with three sequential
samples per provider and Go 1.26.3. Relative to the
[initial comparison](2026-10-06.md), the benchmark script, workflow, Go sources,
module files and guest image were unchanged. The intervening source changes
were the host task-budget fix and its report. Source SHAs differ but measured
commands and code are identical. Both providers used the same SHA within this run.

Raw data: [2026-10-06-expanded-samples.json](2026-10-06-expanded-samples.json).

| Median seconds | Original Chickadee 2 CPU / 2 GiB | Expanded Chickadee 4 CPU / 4 GiB | Fresh GitHub 4 CPU / ~16 GiB |
| --- | ---: | ---: | ---: |
| Cold build | 15.240 | 10.562 | 12.491 |

Expanded Chickadee cold build/test sums ranged from **34.657–35.519 seconds**;
the fresh public runner ranged from **34.699–40.656 seconds**. Job execution
ranged from **51–54 seconds** on Chickadee and **50–59 seconds** hosted.
Complete job execution includes setup, cached repeats, artifact upload and post
steps; it excludes queue waiting. Method and cache limitations are described
in the initial report. The original-profile column uses that earlier run;
the hosted column here is a fresh contemporaneous baseline.

## Interpretation

Additional resources improved this particular workload materially. Because CPU
and RAM changed together, this does not isolate their contributions. More
memory alone, more vCPUs alone, QEMU overhead, disk performance and throughput
remain unmeasured. Three samples are a small experiment, and public-runner
variation is visible; the result does not guarantee that Chickadee will win for
other jobs or future runs.

The host has four logical CPUs. The matrix ran only one active job at a time;
two simultaneous 4-vCPU guests share those host CPUs. The extra vCPUs improve
one-job latency but do not add physical capacity. A concurrency-two benchmark
is needed before making throughput or service-capacity claims.

## Deployment outcome

The pilot remains enabled on **4 vCPU / 4096 MiB memory / 16 GiB disk per guest**,
with warm pool 1 and maximum 2 guests. Host capacity was checked before the
change; two 8-GiB guests would have left insufficient host memory. The service
was stopped while idle, its config and persistent resource drop-in were updated,
and a new independent warm guest booted before dispatch.

Finite service limits were recomputed using the existing installer formulas:
9728 MiB aggregate memory, no swap, 800% aggregate CPU quota and 392 host tasks.
An 800% quota permits the configured guests to share CPU time; on a four-CPU
host it does not provide eight physical CPUs. Kernel cgroup settings were
checked. No task-limit rejection occurred after restart. Each benchmark VM
exited and its overlay was removed; a new credential-free warm guest was READY.

The portable example configuration remains a small starting profile. On another
host, choose resources within available capacity and recompute the service
drop-in before changing guest settings, as described in the installation guide.
The shared-UID trust limitations and outstanding release acceptance checks are
unchanged. This experiment does not establish paid-service readiness.
